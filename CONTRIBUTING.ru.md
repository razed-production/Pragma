# Вклад в Pragma

Pragma намеренно строится вокруг аккуратного и долгоживущего фундамента. Вклад приветствуется, но архитектурная дисциплина здесь важнее, чем быстрые эксперименты ради одной фичи.

## Базовые Правила

- только Windows desktop
- только `x64`
- только 3D
- `C++20`
- публичные модули движка должны оставаться graphics-API neutral
- `Renderer` не должен зависеть от `ID3D11*`
- код DX11 должен жить только в `RHI/DX11`

## Перед Изменением Кода

1. Прочитать [docs/ARCHITECTURE.md](./docs/ARCHITECTURE.md).
2. Проверить [docs/PROJECT_LAYOUT.md](./docs/PROJECT_LAYOUT.md).
3. Если изменение затрагивает rendering-контракты, прочитать [docs/RENDERING.md](./docs/RENDERING.md).

## Ожидания От Вклада

- предпочитать небольшие и обозримые изменения
- держать правила владения и lifetime явными
- не протаскивать backend-specific assumptions в общие заголовки
- документировать назначение и границы каждой новой подсистемы
- обновлять документацию в том же изменении, если меняются setup, архитектура или workflow

## Правила Для Рендера

- новые renderer-фичи должны идти через `Renderer -> RHI`, а не напрямую в backend
- контракты `RHI` должны оставаться совместимыми с будущей explicit API моделью
- DX11 должен оставаться implementation detail и compatibility backend

## Правила Для Assets

- лучше использовать `AssetId`, чем захардкоженные пути в engine-коде
- imported asset data и runtime GPU resources должны оставаться разными сущностями
- новый asset format нужно сопровождать описанием допущений и ограничений

## Минимальная Проверка

- `Debug|x64` успешно собирается
- приложение запускается
- resize продолжает работать
- камера и ввод работают корректно
- сцена по-прежнему рендерится через абстрактный путь

## Документация

Если изменение затрагивает onboarding, архитектуру, сборку, runtime flow, editor workflow или точки расширения, нужно обновить соответствующий документ в [docs](./docs).
